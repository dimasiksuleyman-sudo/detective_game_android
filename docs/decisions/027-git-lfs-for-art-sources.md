# ADR-027: Исходники ассетов в Git LFS; позже — свой сервер или S3

**Дата:** 2026-11-12 · **Статус:** принято

## Контекст

Оригиналы арта и аудио (`art/`) пилота — около 160 МБ в обычном git, на каждое новое дело добавится ещё 150–200 МБ. Каждый клон тянет всю историю, репозиторий быстро разрастается.

## Варианты

1. **Git LFS на GitHub.** Бесплатно 10 ГБ хранения и 10 ГБ трафика в месяц; без привязанной карты лимит просто блокирует загрузку, денег не списывает.
2. Свой сервер №2 (rsync/MinIO).
3. S3-совместимый бакет (облако).

## Решение

- Сейчас — **Git LFS**. В `.gitattributes`: `art/**/*.{png,jpg,jpeg,webp,mp3,wav}` → LFS. Готовые файлы игры в `public/` остаются в обычном git: они маленькие и нужны для сборки.
- **История не переписывается.** 65 файлов, закоммиченных до перехода, перечислены в `.gitattributes` с `-filter` и остаются обычными. Перенос их в LFS потребовал бы force-push `main`.
- **Проверка в CI:** `npm run lfs:check` (`tools/check-lfs.ts`). Любой новый исходник в `art/` должен быть LFS-указателем, иначе CI красный.
- **Экономия трафика:**
  - CI LFS не скачивает: `actions/checkout` по умолчанию без LFS;
  - агенты клонируют с `GIT_LFS_SKIP_SMUDGE=1` и подтягивают нужные файлы точечно (`git lfs pull --include=...`), только если правят арт.

## Последствия

- У всех, кто коммитит арт, должен быть установлен Git LFS (`git lfs install`). В Git для Windows он обычно уже есть.
- **Когда переходить на свой сервер или S3:** если трафик LFS систематически упирается в 10 ГБ в месяц или хранение подходит к 8 ГБ. План перехода:
  - оригиналы выгружаются в бакет `art-originals/<дело>/...` (MinIO на сервере №2 или облачный S3) через `rclone`;
  - в git остаётся манифест `art/REMOTE.json` с путями и SHA-256;
  - LFS-указатели удаляются новым коммитом, историю не переписываем.

  Решение и выбор хранилища — за владельцем.
